## Professional Self-Assessment

Completing this program, and building the ePortfolio that follows this assessment, has clarified something I wasn't fully certain about when I started: what kind of computer science work I actually want to do. I came into the program aiming at data analysis. Through the coursework, and especially through the enhancement work in this capstone, I found I'm drawn more to database administration — designing schemas, managing data security, and keeping systems reliable — with software development as a strong second direction if that path doesn't work out the way I expect. That shift didn't happen because of a single course; it happened because I kept being handed real code with real problems to find and fix, and I noticed which parts of that work I actually wanted to keep doing after the assignment was over.

### Collaborating in a Team Environment and Communicating with Stakeholders

My clearest experience with both of these is not from a classroom project but from my job as a warehouse operator, where a meaningful part of the work is explaining technical or process issues to coworkers and supervisors who don't have a technical background. That's a genuinely different skill than explaining something to another programmer — it means figuring out what someone actually needs to know to make a decision or do their job safely, and leaving out the parts that don't serve that, without talking down to them or oversimplifying to the point of being wrong. I carried that same instinct directly into this capstone. When I wrote my enhancement narratives, I didn't just document what changed in the code; I was explicit about what I could verify myself and what still needed a human in the loop — like flagging that I couldn't compile my Android database artifact in my own environment and needed a real build-and-run pass before anyone could trust it. That's the same underlying skill as the warehouse work: telling someone exactly what they can rely on and what they can't, rather than letting confidence in my own explanation stand in for actual certainty.

I also built toward this more directly in two of my three artifacts. Both my C++ graphics artifact and my Java data structures artifact now expose a live, browser-based dashboard showing real system data — frame rate and camera state in one, hash table load and collision counts in the other — specifically so someone without programming knowledge could open a page and see what the system is actually doing, instead of that information being locked inside a codebase only I could read. That's a small piece of infrastructure, but the intent behind it is the same one I bring from the warehouse floor: technical work only has value to an organization if the people who aren't technical can still see and trust what it's doing.

### Data Structures and Algorithms

My clearest demonstration of this is the algorithms enhancement in this capstone, where I replaced a linear-search ArrayList with a hash table I built myself — not just swapping in a library HashMap, but writing my own separate-chaining implementation with observable collision tracking and load-factor-driven resizing, specifically so the trade-off between memory use and lookup speed wasn't hidden inside someone else's code. But that thinking started earlier in the program, in courses like Data Structures and Algorithms, where I first worked through the real difference between an approach that's simple to write and one that actually performs well as a dataset grows. What's changed since then is that I no longer treat Big-O complexity as a classroom exercise — I now default to asking what a given data structure choice will cost as a system scales, the same way I'd ask that about a warehouse process that works fine at low volume but breaks down during a holiday rush.

### Software Engineering and Database

Across my software engineering and database work in this program, the consistent thread has been learning to distrust code — including my own — until I've actually verified it. In my graphics artifact, a code review surfaced a function that was supposed to free GPU memory but was actually leaking it, and a lookup function that always reported success whether or not it had found anything. In my database artifact, an artifact literally named for encryption turned out to have none at all, alongside passwords compared as plaintext directly in a SQL query. None of those defects were visible from the code's structure or its comments; they only became visible when I actually read the logic line by line and, wherever I could, compiled and ran the code to confirm it. That habit — verify before you trust, and say plainly when you couldn't verify something — is the biggest single change in how I approach software engineering and database work now compared to when I started the program.

### Security

Security shows up most directly in my database enhancement — real encryption at rest, salted password hashing, and a database key that's generated randomly and stored through the Android Keystore rather than hardcoded in source, specifically because a hardcoded key would have made the encryption almost cosmetic. But I made a point of carrying that mindset into my other two artifacts as well, even though neither is in the databases category: I reviewed both for hardcoded credentials or secrets, and my algorithms artifact includes input validation against an explicit allow-list rather than accepting arbitrary data. Security, to me, isn't a category of work I do sometimes; it's a question I now ask about every piece of code I touch, regardless of what that code is officially about.

### How the Artifacts Fit Together

The three artifacts in this portfolio were not built at the same time or originally designed to work together, but taken as a set, they tell one consistent story. The **software engineering artifact**, a C++ OpenGL rendering application, demonstrates my ability to diagnose and correct real defects in an unfamiliar codebase and to modernize its architecture using current design patterns. The **algorithms artifact**, a Java rescue-animal management system, demonstrates the same defect-finding discipline applied to a project that, as I discovered once I actually tried to compile it, didn't even build in its original state — and it demonstrates my ability to design and justify a real data structure from first principles rather than just calling a library function. The **database artifact**, an Android inventory application, demonstrates applied security engineering: closing gaps between what a system claims about itself and what its code actually does.

Each artifact was enhanced honestly, with real defects fixed and real trade-offs documented, and each one was verified as thoroughly as my available tools allowed — compiled and tested directly wherever I could, and clearly flagged for further verification where I couldn't. That combination — technical range across three different languages and problem domains, paired with consistent honesty about what's actually been confirmed — is what I want this portfolio to demonstrate about how I'll work as a computer science professional, whether that ends up being in database administration or software development.
